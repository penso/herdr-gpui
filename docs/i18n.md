# Internationalization

How Herdr UI shows its text in any language, and how to add a message or
a language. The app is ready for Chinese, Japanese, Korean, and
right-to-left languages such as Hebrew, but only English (`en-US`) ships.
Not every string is a message yet: see [What is left](#what-is-left).

## Where things are

```text
crates/herdr-i18n/                   no GPUI
  src/locale.rs                      Locale, Direction, Pseudo, Language (the setting)
  src/negotiate.rs                   the system's languages, negotiation (fallback en-US)
  src/catalog.rs                     the Fluent catalog over the embedded files, endonyms
  src/pseudo.rs                      the en-XA / en-XB transforms
  src/cjk.rs                         which regional Han glyphs a language wants
crates/herdr-gpui/locales.rs         build script: embeds and checks the files,
                                     writes the table fl! checks against
crates/herdr-gpui/src/i18n.rs        fl!, i18n::message, the current locale global
crates/herdr-gpui/src/direction.rs   logical sides and mirrored icons for RTL
crates/herdr-gpui/locales/<tag>/     one .ftl file per feature module, per language
  language.ftl                       the language's name in itself
  commands.ftl, palette.ftl, settings-*.ftl, menus.ftl, ...
scripts/check-i18n.py                just check-i18n
assets/macos/Info.plist              CFBundleDevelopmentRegion, CFBundleLocalizations
scripts/release/installer/<tag>.isl  the Windows installer's own text
scripts/release/so.pen.herdr-gpui.desktop   the Linux desktop entry
```

The `language` setting in `config-gpui.local.toml` is `system` (the
default) or a BCP 47 tag. Settings > General > Language picks it from
System and the languages there are, each named in itself; `herdr-gpui
language set TAG` writes the same key. The locale is a GPUI global:
changing it swaps the process-wide catalog, reinstalls the menus, and
redraws every window. Text a view already built (an open palette, a
dialog's field) keeps its language until it is built again.

## Adding a message

1. Pick the feature's file, `crates/herdr-gpui/locales/en-US/<feature>.ftl`,
   or add one for a new feature. One file per feature module keeps parallel
   pull requests out of each other's catalogs.
2. Name the message with the file's name as its prefix:
   `worktree-popover-delete = Delete` lives in `worktree-popover.ftl`. IDs
   are stable identifiers, not English text: changing what a message means
   takes a new ID, so translations of the old meaning do not linger.
3. Say who reads it and what its variables hold in a `#` comment above it
   when the English alone leaves room for doubt. Translators see only the
   file.
4. Show it with `fl!`:

   ```rust
   use crate::i18n::fl;

   fl!("palette-placeholder")
   fl!("palette-count", shown = 3, total = 9)
   ```

   A call naming no English message, an argument the message does not
   take, or one it leaves out fails to compile at that call.
5. Run `just check-i18n`. It also fails on an English message nothing uses.

Rules for the English text:

- Arguments are named (`{ $count }`), and a sentence is one message. Never
  build a sentence from translated fragments in Rust, or join a message
  with `format!`: word order differs between languages.
- Plurals go in the message, as Fluent selectors on the number, not in
  Rust:

  ```ftl
  sidebar-tab-count = { $count ->
      [one] One tab
     *[other] { $count } tabs
  }
  ```

  Languages without plurals (Chinese, Japanese) keep only `*[other]`;
  those with several (Polish, Arabic) add `[few]`, `[many]`, and so on.
- Fluent wraps every placeable in Unicode isolation marks (FSI, PDI), so a
  Latin branch name stays readable inside a Hebrew sentence. Text that
  leaves the window (command line output, a search's English match) comes
  from `i18n::english`, which has no marks.
- Names users chose (workspaces, branches, hosts), daemon and agent text,
  terminal content, config keys, `--json` keys, logs, and commit messages
  are never messages. See [Scope](#scope).

Code that picks a message ID as data, as the command catalog and Settings'
tables do, calls `i18n::message(id, &args)` instead of `fl!`, and a test
checks the table against the English files with `i18n::takes(id)`.

### Marking a module migrated

Once a module shows only messages, put `// i18n: migrated` near its top.
`just check-i18n` then rejects any string literal in that file, or in the
directory of the same name, that reads as English. Logs, panics,
`#[error]` attributes, `write!` in a `Display`, key contexts, and bindings
are exempt. A literal that is data (a font or theme name, a config value)
takes `// i18n: data` at the end of its line or on the line above.

### Layout that survives other languages

- Widths: `en-XA` makes every message about 40% longer, and CJK text is
  shorter but taller. Let rows wrap or truncate rather than sizing them to
  English.
- Cut text with `truncate.rs`, which counts grapheme clusters, never by
  bytes or `char`s.
- Sides: write `ps`/`pe`, `ms`/`me`, `border_s`/`border_e`, `text_start`,
  `row()` from `direction::Logical` instead of left and right, `anchor` for
  popovers, `toward_end` for slides, and `icon`/`glyph` for chevrons and
  arrows that point along the line. See [Right to left](#right-to-left).

## Testing with the pseudo-locales

Two locales are generated from the English messages at run time, never
written as files:

| Locale | Shows | Catches |
| --- | --- | --- |
| `en-XA` | Accented, about 40% longer, bracketed: `[Šéţţîñĝš]` | Text that is not a message, labels clipped short |
| `en-XB` | English drawn right to left, with the layout mirrored | Chrome that does not mirror, icons pointing the wrong way |

Switch to one with QA > Pseudo-Locale (turn on `[features] qa_menu`), or
`herdr-gpui language set en-XA`; `language set system` goes back.

Each window keeps an `en-XA` leak test in its module's `tests/en_xa.rs`:
`i18n::leak_tests::under_en_xa` opens the surfaces, `draw` records each
line GPUI shapes, and `assert_translated` fails on a line without the
pseudo-locale's brackets. Shortcut keys and data such as user names are
passed as allowed. Today the palette (Commands and Go To), every Settings
page, every Cloud devices card, the menu bar, the log window, the theme
picker, code tabs, App Updates, and each stage of Teleport have one; a
module migrated later adds its own.

## Adding a language

A language is a directory of messages plus a line in each platform's
packaging. With `fr` as the example:

1. **Messages.** Create `crates/herdr-gpui/locales/fr/` with a copy of any
   English `.ftl` files you translate, under the same names, IDs, and
   arguments. A message a translation leaves out shows in English. A
   translation may not define an ID English lacks.
2. **Its name.** Add `locales/fr/language.ftl` with
   `language-name = Français`: the language's name in itself, which
   Settings and `herdr-gpui language list` show whatever language the app
   is in.
3. **macOS.** Add the tag to `CFBundleLocalizations` in
   `assets/macos/Info.plist`, so the system's own menu items (Services,
   Emoji & Symbols, Enter Full Screen) and Language & Region list it.
   Optionally add `assets/macos/fr.lproj/InfoPlist.strings` translating
   the `NS…UsageDescription` prompts; the bundle and release packaging
   copy every `*.lproj` there into `Contents/Resources`.
4. **Windows installer.** Copy `scripts/release/installer/en-US.isl` to
   `installer/fr.isl` and translate its values, then add a line to
   `[Languages]` in `scripts/release/herdr-gpui.iss` that pairs Inno
   Setup's translation of its own wizard with it:

   ```ini
   Name: "french"; MessagesFile: "compiler:Languages\French.isl,installer\fr.isl"
   ```

   Setup picks the one matching Windows' display language, and asks only
   when none does.
5. **Linux desktop entry.** Add `Comment[fr]=…` under `Comment` in
   `scripts/release/so.pen.herdr-gpui.desktop`; a tag with a region takes
   an underscore (`Comment[pt_BR]`). `Name` is the product's and stays.
6. **Check it.** `just check-i18n` fails when a language lacks
   `language-name`, an installer file, or a `Comment[tag]`, when it defines
   an ID English has not, when `CFBundleLocalizations` leaves it out, or
   when the plist, an `.lproj`, an installer file, or a desktop key names a
   language that has no messages. The `.lproj` is the only optional part.
   The installer's `[Languages]` line is checked by
   `scripts/release/tests/test_windows_package.py`. Then pick the language
   in Settings and look over the windows in it.

The tag is the directory's name everywhere: `fr`, `pt-BR`, `zh-Hans`,
`he`. Negotiation matches regions and scripts, so `fr` serves `fr-CA`
unless `fr-CA/` exists too.

A right-to-left language (Hebrew, Arabic, Persian, Urdu) needs nothing
more: `Locale::direction` knows it from the tag, and the windows mirror.

## Platforms

- **macOS.** `CFBundleDevelopmentRegion` is `en-US` and
  `CFBundleLocalizations` lists the language directories, which
  `just check-i18n` keeps in step. macOS picks the bundle's localization
  from the system's preferred languages (or the app's entry under System
  Settings > General > Language & Region > Applications), not from the
  `language` setting: with `language = "fr"` on an English system, the app's
  own text is French while the menu items macOS adds stay English. The
  traffic lights move to the right only when that system choice is a
  right-to-left localization, so under `en-XB` they stay on the left.
- **Windows.** The installer's wizard uses Inno Setup's translations and
  its own text comes from `installer/<tag>.isl`; registry text it writes
  (the "Open in Herdr UI" folder command, the link type's name) is in the
  language Setup ran in. `site/install.ps1` is English only. The window
  itself follows the `language` setting.
- **Linux.** The desktop entry's `Comment` is localized by `Comment[tag]`
  keys; launchers pick it from `LANGUAGE`/`LC_MESSAGES`.

The macOS text system draws Hebrew right to left and isolation marks
invisibly; on Windows, GPUI's DirectWrite path draws a right-to-left run's
glyphs in the wrong order. See [Right to left](#right-to-left).

## What is left

Phase 2's string migration is not finished. Merged: the command catalog,
the palette's own text (#874), the Settings window and the menu bar (#880),
the language picker (Phase 5), the tab, pane, and group menus with the
close confirmation and the dialogs' text field, and the code view and
editor, the log window, the theme picker, App Updates and its release
notes, Teleport's dialog, and the palette's Go To and project rows and
badges. Most of the app still shows English literals:

- Dialogs and popover menus in `menu/` (about 700 literals): the worktree
  popover and its dialogs, devices, Git and pull requests, sessions, and
  the rest. The pane menu's move to another device still shows Teleport's
  steps and summaries in English.
- The main window's notices: toasts, flashes, and the input, paste,
  transfer, find, copy mode, and annotation text in `window/`, the
  notifications in `notifications/`, and the tab faces' muted hint in
  `tab_layout`. The sidebar, title bar, status bar, tab strips, and empty
  states are messages; the nameless `agent` and `workspace` fallbacks stay
  English while other areas borrow them, and the local device keeps its
  `Local` label, which sidebar rules match.
- The activity bar's panels and pages: Overview, Orchestrator, pull
  requests, issues, Security, Review, Usage, Automations
  (`overview/`, `orchestrator/`, `pull_request/`, `security/`, `review/`,
  `usage/`, `automations/`), and the devices overview.
- Chats (`chat/`) and the browser (`browser/`).
- Localized error messages. Errors still reach the window as an `$error`
  placeable holding their English `Display`. The plan is a localized
  message per user-facing error enum, chosen by variant at the
  presentation boundary and delegating through wrapped crate errors
  (`GitHub(#[from] herdr_github::Error)`), with English `Display` kept for
  logs.
- Text Settings shows from other crates: herdr-remote engine errors,
  Azure VM size and price summaries, cloud job status, and
  `remote::device_line`.
- Hand-built relative times and plurals: `herdr-vcs`'s
  `checkpoint.rs` ("3 min ago") and `remote.rs`'s "Last seen", and the
  remaining hand-built plurals, should become Fluent selectors.
- `en-XA` leak tests for each of those surfaces, until every window and
  popover has one.

Command line `--help` and `herdr-gpui` command output stay English by
decision, as do `--json` keys.

## Decisions

| Question | Decision |
| --- | --- |
| Message format | [Project Fluent](https://projectfluent.org) (`.ftl`): CLDR plural and gender selectors live in the translation, and placeables are wrapped in Unicode isolation marks (FSI/PDI) so Hebrew text stays readable around Latin names. |
| Rust stack | `fluent-bundle`, `fluent-langneg`, `unic-langid`, through `i18n-embed`'s loader. `fl!` checks message IDs and arguments against the English files at compile time, as `i18n-embed-fl` does for System76's COSMIC desktop, but is the app's own: `i18n-embed-fl` reads one `.ftl` file per language, and every feature keeps its own file (see [Where things are](#where-things-are)). |
| System locale | `sys-locale`, negotiated against available locales with `fluent-langneg`, falling back to `en-US`. |
| Formatting | Fluent `NUMBER()` and plural selectors first; ICU4X (`icu` 2.x) only where a formatter is genuinely needed (dates, lists). |
| Alternatives rejected | `rust-i18n` (no plurals or isolation; still driven via `gpui_kit::set_locale` if gpui-kit lands), gettext (weak plural model, English-as-key), MessageFormat 2 (no production-ready Rust implementation yet; revisit later). |
| Error messages | Translated. Typed errors keep their `thiserror` English `Display` for logs; users see a localized message chosen by variant at the presentation boundary. |
| Translations shipped | English only. Pseudo-locales are generated at runtime for testing, never written as files. |

## Scope

Translated: command labels, menus, the settings window, dialogs, tooltips,
the status bar, empty states, notifications the app writes, relative times,
and user-facing error messages.

Never translated: terminal content, text from the daemon, agents, Git, or
GitHub; names users chose (workspaces, branches, hosts); config keys and
command `name`s; `--json` output and its keys; logs, diagnostics, and crash
reports; commit messages and other text the app writes into repositories;
CLI `--help` (deferred).

## Right to left

`direction.rs` reads the shown locale's direction where there is
no app context, as text is, and gives every styled element logical sides
(`Logical`: `row`, `ps`/`pe`, `ms`/`me`, `inset_s`/`inset_e`,
`border_s`/`border_e`, `rounded_e`, `text_start`/`text_end`), plus
`anchor` for popovers, `toward_end` for slides and drags, and `icon` and
`glyph` for the icons and text arrows that point along the line (chevrons,
Back and Forward, panels, `▸`, `›`). The window body, sidebar, activity
bar, rail, title bar, status bar, Settings window, command palette, pane
and group menus, switches, and the menus' anchors use them, and each
window sets its text from the start. Under `en-XB` the sidebar leads from
the right, slides out to the right, and resizes by its left edge.

- What stays left to right: the terminal grid and its content, and with
  them panes, splits, and tab strips, which are the daemon's geometry and
  what directional pane commands act on; sliders, whose value grows to the
  right; and the window's frame and resize edges. Right to left, the tab
  row never stands in for the title bar, since one row cannot read both
  ways, so the window keeps its full-width header.
- macOS keeps the traffic lights on the left whatever language the app
  shows; only the system's own layout direction moves them, which needs a
  right-to-left localization in the bundle, chosen by the system's
  languages (see [Platforms](#platforms)). A mirrored title bar
  clears them on its end. Client-drawn window controls on Windows and Linux
  move to the left, as Windows puts its own.
- Text fields (`caret.rs`): GPUI's `x_for_index` and `closest_index_for_x`
  assume glyphs in byte order, so in a Hebrew run the caret stayed at the
  run's left edge. `Carets` keeps the shaper's glyph positions and resolves
  each character's direction with `unicode-bidi` (paragraph direction from
  the first strong character, as CoreText and cosmic-text use), so the
  caret, clicks, a selection drawn as one stretch per direction, and the
  input method's box follow what was drawn. Arrows and deletion still move
  in logical order, as every platform's own fields do, and a line that fits
  sets against the field's right.
- Per platform, checked by the native sidebar fixture (`smoke_bidi.rs`),
  which shapes with the platform's text system:
  - macOS (CoreText), run natively: FSI and PDI take no room and never draw
    the missing-glyph box; Hebrew is drawn right to left; the caret follows
    it through mixed text.
  - Linux (cosmic-text): GPUI places each glyph at the x its layout run
    gives, in visual order, and has its own mixed-direction tests. Not run
    natively for this change; the fixture reports it where it runs.
  - Windows (DirectWrite), from GPUI's source, not run natively: the
    layout runs bidi analysis and shapes RTL runs, but GPUI's `DrawGlyphRun` callback ignores the run's
    `bidiLevel` and its right-edge origin, placing glyphs left to right in
    the order it is handed them, so a Hebrew word is drawn backwards. The
    app cannot correct this; it needs a change in GPUI's
    `gpui-pre-windows` text system. The `windows-native` CI job runs the
    fixture and reports the order it finds rather than failing on it.
- `en-XB` draws every message's letters right to left whatever the layout,
  and Fluent transforms each run of a message's text apart from its
  placeables, so a message with numbers reverses piece by piece around
  them. Real right-to-left translations will not do that.

## Chinese, Japanese, and Korean

`herdr_i18n::CjkScript` reads which regional Han glyphs a
language wants (Simplified, Traditional, Hong Kong, Japanese, Korean), and
`config/cjk_fonts.rs` holds each platform's families. When a face's
`fallback` is unset, the sidebar, tab, and interface faces search the
installed icon fonts, then one installed CJK family per script, the script
of the first CJK language in the `language` setting or the system's
languages first; the setting counts before any translation in that
language ships. The terminal keeps the icon cascade alone. The app's own
cuts (`truncate.rs`) count grapheme clusters, or columns where the budget
is a width, and SearchInput's arrows and deletion step over whole clusters
as DialogInput's already did. GPUI's width-based `text_ellipsis` still
cuts between `char`s inside GPUI; CJK text is unaffected, but a combining
mark or emoji sequence at the cut can lose its tail there.

### Survey, when the plan was made

- **Zed** has no internationalization: no catalogs, no locale handling, every
  string a literal. GPUI has no layout direction concept.
- **gpui-kit** uses `rust-i18n` with one YAML file holding every language per
  key (`crates/component/locales/ui.yml`, `rust_i18n::i18n!("locales",
  fallback = "en")`, `gpui_kit::set_locale`). It has no plural rules and no
  bidirectional isolation.
- **GPUI text** already shapes bidirectional text (CoreText on macOS,
  cosmic-text with `unicode-bidi` on Linux) and wraps CJK text without spaces
  (`LineWrapper`). The Windows DirectWrite path passes `bidiLevel: 0`, so RTL
  shaping there must be verified.
- **Herdr UI then**: about 1,700 Rust files and 409k lines with inline
  literals, `&'static str` command labels in `herdr-commands`, hand-built
  relative times (`herdr-vcs/src/checkpoint.rs`), about 27 hand-built plurals,
  and `thiserror` messages shown to users.
